Why RSA: update the plan when the world has moved on

The story behind the method, from an unavoidable inference delay to a short feedback correction.

  1. Inference takes time; the scene keeps changing. A VLA observes the robot and scene at obs(t), then spends time encoding images, processing context, and generating an action chunk. By the time that chunk returns, the observation is obs(t+Δ). In moving-object grasping or precise box folding, this gap can make an otherwise useful plan stale. Figure 1 shows the timing problem.
  2. Asynchronous execution keeps actions available, but fresh feedback is still needed. Running the VLA alongside the previous action chunk avoids waiting through the full inference interval. It does not update the observation used to generate the returning chunk. Re-querying the full VLA on the latest observation would incur another long delay. RSA instead reuses the returned plan and retained context as the starting point for correction.
  3. Teach a small network how the frozen VLA would revise that plan. Using the existing SFT dataset, we simulate random delays and ask the same frozen VLA for chunks at obs(t) and obs(t+Δ). Shared sampling noise pairs the stale chunk with its teacher chunk. A DiT learns Brownian-bridge endpoint matching from the stale source toward the teacher output through endpoint MSE. The Schrödinger-bridge perspective motivates the distribution update; RSA uses paired bridge supervision rather than claiming an exact optimal bridge solution. Figure 2 shows this distillation process.
  4. Spend a short wait to let the latest observation affect the next action. At handoff, the controller pauses its action cursor, reads the latest observation, and holds the last command until the rectifier finishes. It then installs the full corrected chunk and starts at index zero. Heavy inference stays asynchronous; the lightweight update is synchronized with execution. This uses the observation at every handoff before issuing the first corrected action. Figure 3 shows the online schedule.

Three connected ideas: combine asynchronous VLA generation with a short synchronous correction; attach a separately distilled rectifier to an already SFT-trained VLA; and incorporate the latest observation at every chunk handoff. The approximately 5 ms correction wait improves feedback freshness while the physical scene continues to evolve.

The two-beat cycle

After a one-off pure-VLA startup, every inference cycle is replan → rectify on one connection.

  1. Startup (t₀). No old chunk exists, so run the VLA once — a pure replan, no rectify — and begin executing chunk₀ from the front. This is the only cycle without a rectify.
  2. Replan on obs_old. The background thread sends the current observation and the frozen VLA runs (~tens of ms), storing stale_chunk + kv_cache for this connection. Control never blocks — it keeps popping the old chunk, so the joint moves continuously.
  3. Measure & compute delta. The instant replan returns, the client measures its latency and sets delta = max(2, ceil(latency × rate)) — the number of control steps the observation has drifted. Never hardcoded.
  4. Rectify on obs_new. Grab the freshest observation and run the lightweight RectifierDiT (~5 ms), reusing the stored stale chunk + kv over the same connection. The VLA does not re-run.
  5. Atomic swap. Replace current_chunk with the rectified chunk and reset the cursor to control_delay (default 0). No crossfade, no dropped frames — the corrected chunk is executed verbatim from the front.

Simulation · Kinetix

Correction under larger delays

At Δ = 4 environment steps, RSA reaches 76.8% success, compared with 61.8% for RTC, 55.7% for BID, and 49.0% for Naive Async. Results average 12 levels and all feasible execution horizons, with 2,048 rollouts per level and delay–horizon pair. Learned variants average three training seeds; each baseline uses one evaluation run.

Kinetix uses a compact MLP-Mixer for symbolic state observations to test the correction formulation. Its discrete correction cost adds no whole environment step, unlike the measured wall-clock DiT wait on the robot. Benefits depend on delay: RTC leads RSA by 2.1 percentage points at Δ = 1.

At Δ = 4, RSA w/o bridge reaches 75.5%. That comparison changes the source, path, and sampler together, so it does not isolate the bridge path alone.

Offline · Recorded Fold Box episodes

Action agreement at unseen delays

Rectifiers trained at Δ = 2–6 are evaluated at Δ = 1–8 using 11 recorded demonstrations at 30 Hz. At unseen delay Δ = 1, RSA's expert-action agreement is 0.622, versus 0.388 without the bridge; at Δ = 8, it is 0.467, versus 0.327.

Agreement requires every component of a normalized 14-dimensional action to be within 0.1 of the expert action. Scores are averaged within each episode and then across episodes; each method and delay uses the same 13,090 timesteps.

This measures offline action agreement, not closed-loop success at unseen delays. Both policy and rectifier use ten sampling steps here; the ~5 ms deployment measurement uses five DiT steps.

Deployment cost

Approximately 5 ms for a complete rectifier pass

The DiT rectifier runs on an NVIDIA GeForce RTX 4090 with five bridge-sampling steps. Approximately 5 ms is the mean across repeated end-to-end measurements, including visual encoding, KV encoding, communication, and host–device transfer. The controller waits for actual completion rather than a fixed timer. The VLA remains frozen, and rectifier distillation reuses its existing SFT dataset.
